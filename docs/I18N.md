# Languages

The screen speaks English, 한국어, 日本語 and 简体中文. Two neighbouring surfaces deliberately do not,
and that is the part worth reading — the rest is a dictionary.

## What is translated, and what is not

| | Who reads it | |
|---|---|---|
| The screen — 324 strings in `static/i18n/<code>.js` | a person | **translated** |
| What the agent is handed — the MCP's `instructions`, table scaffolding, the absence rule | a model | **English, on purpose** |
| The LLM prompts in `ontology/service/server.py` | — | **no language setting at all** |
| The ontology — `vocab.yaml`, `use_when`, the documents | both | **the team's own words. Not ours to restate.** |

### Why the agent's text stays English

It is instruction text for a model, not prose for a reader, and one of those instructions is the
**absence rule** — *only hop 0 may say something is not here*. The whole design rests on it. A
mistranslation there is a correctness bug that no check can see, in a sentence nobody would think to
re-read, for no gain: models follow English instructions at least as well as any other language, and
the rows inside those tables are already in the team's own language, because they are the team's data.

About 28 sentences, against 324 on the screen. Small payoff, concentrated risk, and the one place
where being wrong is not cosmetic.

### Why the prompts have no language setting

They already do the right thing without one. Measured against the live API, with nothing in any prompt
saying what language to answer in:

```
"Billing"    + English description  →  How do I track a payment before it settles · Where is my payment…
"급여"        + Korean description   →  급여명세서 항목 계산 · 4대보험 공제 계산 · 급여 공제 항목
"経費"        + Japanese description →  領収書の保管方法は · 法人カードで支払える経費は
"Beschaffung"+ German description   →  Wie registriere ich einen Lieferanten · Wer gibt welche Beträge frei
```

The content decides, which is correct — a drafted `use_when` is written **into the ontology**, so it
must match the ontology, not the person's menu. Including the case that looked risky: area names are
forced to ASCII kebab-case, so a Korean install's area is literally called `payroll`, and `payroll`
plus a Korean one-liner still comes back Korean.

A language setting here would make it worse. Someone reading the screen in Korean and contributing to
an English ontology would start pushing Korean sentences into English data.

## How the screen decides which language to show

1. What this browser last chose, from `localStorage`.
2. Otherwise the browser's own `navigator.languages`, matched on the base tag — `ko-KR` → `ko`,
   `zh-Hans-CN` → `zh`.
3. Otherwise English.

**Per viewer, not per install.** One install is a team's ontology, and an install-time setting would
serve everyone the language whoever ran the installer happened to speak. Nothing is sent to the
server, nothing is written to the repository, and changing it costs no round trip — the dictionaries
are already loaded.

Per **key** fallback to English, so a half-finished language renders as English where it is missing
rather than as blanks, and a new string is never blocked on being translated four times before it can
ship. An unknown key renders as itself, so a typo shows up as `knowledge.thing` rather than as nothing.

## Adding a language

1. Copy `static/i18n/en.js` to `static/i18n/<code>.js`, change the last line of the header and the
   `IRISI18N_DICTS.<code>` assignment, and translate the values. Keys and order stay as they are.
2. Add `<code>` to `NAMES` in `static/i18n.js`, spelled **in that language** — a person scanning a
   menu looks for the word they would write it with, not for "Korean" in English.
3. Add a `<script>` tag for it in `static/knowledge.html`, before `i18n.js`.
4. `node check/i18n-check.mjs`.

The picker builds itself from the dictionaries that actually loaded, so there is no list to update; a
file that fails to load shrinks the menu rather than offering a choice that does nothing.

Nothing forces a language to be complete. `check/i18n-check.mjs` reports coverage — `ko: 300/324
(93%)` — and only fails on things that are actually broken.

### What the check fails on

* **A key defined twice.** In an object literal the later one wins, silently. This has cost five
  fixes that were reported as done and never reached the screen.
* **A key in a translation that is not in English.** English is the baseline and the fallback, so a
  key only a translation has is a string nobody will ever see — usually a rename applied to one file
  and not the others, which means the English screen quietly lost a label.
* **Placeholders that do not match.** A translation that drops `{n}` renders `removing / — …`; one
  that invents a name renders the braces literally, because `format()` leaves an unknown name alone
  rather than guessing.
* **A key the screen asks for that English does not define.** It renders as its own dotted identifier.
* **Text in `knowledge.html` with no `data-i18n`.** This is how a string escapes the whole system: it
  renders, it looks right in English, and no dictionary has ever heard of it. The map legend was five
  of these, found only by looking at a Korean screen and seeing English words on it.

## Known limits

**Right-to-left is not supported.** The map is an SVG laid out in absolute coordinates; `dir="rtl"`
changes the text direction and nothing else, so Arabic or Hebrew would render mirrored against a
left-to-right diagram. That is a layout job, not a dictionary.

**API error messages are still English.** They reach a person through the screen's toasts, so a
Korean screen can still raise an English sentence. The fix is not to translate them server-side —
agents read the same errors, and it would scatter human-facing text across Python where the check
cannot see it — but to give the errors codes and let the screen translate by code, falling back to the
server's English text for codes it does not know. Most of the ~94 never reach a person, because the
screen refuses bad input with its own words first; the handful that do are the dirty tree, an id
already taken, validation failing, a budget exceeded and a name too long.
