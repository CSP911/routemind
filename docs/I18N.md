# Languages

The screen speaks English, 한국어, 日本語 and 简体中文. Two neighbouring surfaces deliberately do not,
and that is the part worth reading — the rest is a dictionary.

## What is translated, and what is not

| | Who reads it | |
|---|---|---|
| The screen — 338 strings in `static/i18n/<code>.js` | a person | **translated** |
| What the agent is handed — the MCP's `instructions`, table scaffolding, the absence rule | a model | **English, on purpose** |
| The LLM prompts in `ontology/service/server.py` | — | **no language setting at all** |
| The ontology — `vocab.yaml`, `use_when`, the documents | both | **the team's own words. Not ours to restate.** |

### Why the agent's text stays English

It is instruction text for a model, not prose for a reader, and one of those instructions is the
**absence rule** — *only hop 0 may say something is not here*. The whole design rests on it. A
mistranslation there is a correctness bug that no check can see, in a sentence nobody would think to
re-read, for no gain: models follow English instructions at least as well as any other language, and
the rows inside those tables are already in the team's own language, because they are the team's data.

About 28 sentences, against 338 on the screen. Small payoff, concentrated risk, and the one place
where being wrong is not cosmetic.

### Why the prompts have no language setting

They already do the right thing without one. Measured against the live API, with nothing in any prompt
saying what language to answer in:

```
"Billing"    + English description  →  How do I track a payment before it settles · Where is my payment…
"급여"        + Korean description   →  급여명세서 항목 계산 · 4대보험 공제 계산 · 급여 공제 항목
"経費"        + Japanese description →  領収書の保管方法は · 法人カードで支払える経費は
"Beschaffung"+ German description   →  Wie registriere ich einen Lieferanten · Wer gibt welche Beträge frei
```

The content decides, which is correct — a drafted `use_when` is written **into the ontology**, so it
must match the ontology, not the person's menu. Including the case that looked risky: area names are
forced to ASCII kebab-case, so a Korean install's area is literally called `payroll`, and `payroll`
plus a Korean one-liner still comes back Korean.

A language setting here would make it worse. Someone reading the screen in Korean and contributing to
an English ontology would start pushing Korean sentences into English data.

## How the screen decides which language to show

1. What this browser last chose, from `localStorage`.
2. Otherwise the browser's own `navigator.languages`, matched on the base tag — `ko-KR` → `ko`,
   `zh-Hans-CN` → `zh`.
3. Otherwise English.

**Per viewer, not per install.** One install is a team's ontology, and an install-time setting would
serve everyone the language whoever ran the installer happened to speak. Nothing is sent to the
server, nothing is written to the repository, and changing it costs no round trip — the dictionaries
are already loaded.

Per **key** fallback to English, so a half-finished language renders as English where it is missing
rather than as blanks, and a new string is never blocked on being translated four times before it can
ship. An unknown key renders as itself, so a typo shows up as `knowledge.thing` rather than as nothing.

## Adding a language

1. Copy `static/i18n/en.js` to `static/i18n/<code>.js`, change the last line of the header and the
   `IRISI18N_DICTS.<code>` assignment, and translate the values. Keys and order stay as they are.
2. Add `<code>` to `NAMES` in `static/i18n.js`, spelled **in that language** — a person scanning a
   menu looks for the word they would write it with, not for "Korean" in English.
3. Add a `<script>` tag for it in `static/knowledge.html`, before `i18n.js`.
4. `node check/i18n-check.mjs`.

The picker builds itself from the dictionaries that actually loaded, so there is no list to update; a
file that fails to load shrinks the menu rather than offering a choice that does nothing.

Nothing forces a language to be complete. `check/i18n-check.mjs` reports coverage — `ko: 300/338
(93%)` — and only fails on things that are actually broken.

### What the check fails on

* **A key defined twice.** In an object literal the later one wins, silently. This has cost five
  fixes that were reported as done and never reached the screen.
* **A key in a translation that is not in English.** English is the baseline and the fallback, so a
  key only a translation has is a string nobody will ever see — usually a rename applied to one file
  and not the others, which means the English screen quietly lost a label.
* **Placeholders that do not match.** A translation that drops `{n}` renders `removing / — …`; one
  that invents a name renders the braces literally, because `format()` leaves an unknown name alone
  rather than guessing.
* **A key the screen asks for that English does not define.** It renders as its own dotted identifier.
* **Text in `knowledge.html` with no `data-i18n`.** This is how a string escapes the whole system: it
  renders, it looks right in English, and no dictionary has ever heard of it. The map legend was five
  of these, found only by looking at a Korean screen and seeing English words on it.

## Refusals

A refusal is a sentence. It is also, for the eight a person can actually walk into, a **name** and the
**values** inside it:

```json
{ "detail": "node corp-card exists",
  "reason": "id_taken",
  "values": { "id": "corp-card" } }
```

`detail` is always sent and is always the whole answer on its own — an agent, a `curl` and any client
that has never heard of `reason` read exactly what they read before. The screen looks for
`knowledge.err.<reason>`, and falls back to `detail` when it has no string. Nothing is translated
server-side: agents read the same errors, and putting human-facing sentences in Python would put them
where `check/i18n-check.mjs` cannot see them.

They are a name **and** values rather than a finished sentence because half of these interpolate, and
because a translation has to be free to put the value somewhere else. Slicing the English apart would
have fixed the word order of every language to English's.

| `reason` | Raised when |
|---|---|
| `tree_dirty` | the data repository has uncommitted changes, so nothing can be written |
| `id_taken` | that address already exists, and an address is permanent |
| `name_taken` | the address derived from the name is taken |
| `validation_failed` | validation refused the write; the details stay English |
| `name_too_long` | the name cannot become a file — see `NAME_MAX` |
| `region_missing` | no such area |
| `no_llm` | a field needs an LLM to draft and none is configured |
| `holds_children` | it holds nodes, and only documents go along with what holds them |

`values.field` is a **token** — `id`, `file_name`, `source` — not an English word, translated through
`knowledge.errfield.*` before it is interpolated. Dropping "file name" into the middle of a Korean
sentence is a half-translated sentence, which reads worse than an English one.

`check/i18n-check.mjs` fails on a `reason` the API emits with no string behind it: that error would
stay English forever, in every language, and nothing else would ever say so. It fails on the reverse
too — a string with no refusal behind it, which is a rename applied on one side only.

**Writing a Korean string?** Korean particles agree with the last sound of the word before them —
는 after a vowel, 은 after a consonant. An interpolated value can be either, and it can be Latin text
where the rule is not even settled, so `{id}는` is wrong half the time and `{id}은(는)` is a form
nobody wants to read. The answer is not a smarter formatter; it is writing sentences where a value is
never followed by a particle: `{id} — 이미 있는 주소입니다`.

## Two things that were not text, and were still wrong in another language

Neither is a string, so no dictionary would have caught either. Both were found by looking at a Korean
screen rather than by reading the code.

**Every timestamp was UTC and said nothing about it.** `when()` sliced the first sixteen characters off
the stamp and swapped the `T` for a space, so a VRF drawn a moment ago in Seoul showed 11:18 while the
clock on the wall said 20:18 — and nothing on screen said which one it meant. It is the reader's own
clock now. A stamp with no zone marker is UTC, because that is what this API writes, and `new Date`
would otherwise read it as local, which is the same mistake with more steps. Both spellings arrive:
overlays write `…Z`, the curator writes `…+00:00`. Fixed width rather than `toLocaleString`, because
the overlay trail lays these out in a column and a locale-native string is a different length every
time.

**A rack's header was measured by counting characters.** `textWidth` beside it already knew a CJK glyph
is about 1.79 latin characters wide; the header multiplied `.length` by a fixed number, so a Korean or
Japanese name came out 19–22% short — and that width is exactly what keeps the header from colliding
with its own buttons. Latin labels are unchanged to the pixel; only CJK gets the room it always needed.

## A name in another script becomes an address

An id is the file name, the URL path and a permanent address, so it is ASCII kebab-case. That used to
mean a team writing in Korean, Japanese or Turkish typed an id **by hand for every entity** while an
English team typed none — seventy-nine of them in the shipped example. Not a rough edge: a different
product depending on the language you work in.

`ontology/service/romanize.py` handles what is mechanical:

| | |
|---|---|
| Latin with marks | `Přehled` → `prehled`, `Küçük Paket` → `kucuk-paket` |
| Hangul | `출장비 정산` → `chuljangbi-jeongsan`, from the Unicode composition, no dictionary |
| Kana | `けいひせいさん` → `keihiseisan` |
| **Han characters** | **refused** — `経費精算` gives nothing |

**The refusal is the feature.** Han readings are a dictionary of thousands, and in Japanese the
reading depends on the compound; a guess is a permanent address that means something else. It goes to
the LLM, which is the only thing that can read it, or to the person.

**One unreadable letter refuses the whole name.** `経費 report` gives nothing even though half of it is
readable. That rule is the original one, kept: `Ürün` reduced by dropping what was not understood
gives `r-n` — not wrong-looking enough for anyone to catch, and it cannot be renamed.

The letters that vanish are asserted one at a time, because a missing table entry announces itself as
a plausible address rather than as an error: `Straße` folds to `stra-e` and `Økonomi` to `konomi`
unless ß, Ø, Đ, Ł, Æ, Þ and their friends are written down.

It is **transliteration, not orthography**. Hangul is romanised from the letters, not the sound: the
Revised Romanization of 학년 is `hangnyeon` and this gives `haknyeon`, because assimilation needs a
pronunciation dictionary. For an address, deterministic and legible beats orthographically perfect —
and the person naming the thing sees the result before it is written, on a screen that says an address
can never change.

`./check/romanize-check.py` — 38 cases, no server. It runs in `smoke.sh`.

## Known limits

**Right-to-left is not supported.** The map is an SVG laid out in absolute coordinates; `dir="rtl"`
changes the text direction and nothing else, so Arabic or Hebrew would render mirrored against a
left-to-right diagram. That is a layout job, not a dictionary.

**Most API error messages are still English, on purpose.** There are 77 refusals in `write.py` and 52
validator diagnostics behind them; the eight a person actually meets are translated and the rest are
not. See "Refusals" below.
