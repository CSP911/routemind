Knowledge

라우팅되는 온톨로지

지식을 검색하지 않습니다. 광고하고, 고르게 하고, 그다음에 읽힙니다. 네트워크 라우팅에서 빌려온 구조이고, 빌려온 것은 은유가 아니라 규칙입니다.

1

Knowledge 자체의 작동 방식

에이전트에게 지식 전체를 주면 못 씁니다. 그래서 라우터가 하는 일을 그대로 합니다 — 목적지 전부를 싣지 않고, 어디로 가면 되는지를 한 줄로 광고합니다.

1-1

라우팅 광고 · 축약 · AS

모든 런은 같은 한 장에서 시작합니다. 이것이 hop 0 입니다.

KNOWLEDGE — the areas of this domain Pick the row whose condition matches the question, then fetch it. One step, then read. KIND ADDRESS WHY YOU WOULD PICK THIS ROW table /v1/regions/clinic booking · check-in · who saw whom when table /v1/regions/library 어떤 책이 있나 · 어디 꽂혀 있나 · 분류가 어떻게 되나 table → knowledge_table({ path }) · file → knowledge_read({ path }) Use the address exactly as printed above. Never build one. Nothing outside this list exists in Knowledge. This list is the grounds on which you may say something is absent — no smaller table is.

실제 출력입니다. 그림이 아니라 에이전트가 받는 문자열 그 자체입니다.

한 줄에 세 가지가 있습니다. KIND 는 어느 도구를 부를지, ADDRESS 는 정확히 무엇을 부를지, USE_WHEN 은 이 줄을 고를 이유입니다. 에이전트는 이 세 칸만 보고 하나를 고릅니다.

부재 판단은 hop 0 에서만 참입니다. 영역 안의 표는 “이 영역이 담은 것”의 목록이지 세상에 대한 주장이 아닙니다. 이걸 흐리면 에이전트가 한 영역 안에서 “그런 건 없습니다”라고 답합니다 — 나머지를 안 보고. 그래서 모든 하위 표 아래에 go back to /v1/regions 가 붙습니다.

1-2

라우팅 승인 및 적용 · LLM 관여 지점

영역에 내용이 늘면 광고 문장이 낡습니다. 담은 것과 말하는 것이 벌어지는데, 그 상태에서는 에이전트가 맞는 영역을 안 고릅니다.

고치는 경로는 하나뿐입니다 — 즉시 적용 경로가 없습니다. 자기 제안도 승인할 수 있지만 반드시 큐를 지나가고, 기록이 남는 것 자체가 안전장치입니다.

Overlay — 여러 영역을 한 런에

질문 하나가 영역 하나에만 걸리지는 않습니다. CDN 과 배포 채널을 같이 봐야 답이 나오는 질문이 있습니다. 그럴 때 고른 영역들을 한 런의 작업 범위로 묶습니다 — VRF 가 여러 인터페이스를 한 라우팅 인스턴스에 묶는 것과 같은 자리입니다.

고른 것은 전부 온톨로지가 인쇄한 주소입니다. 영역이든 개체든 섞을 수 있습니다. 쿼리 파라미터 root 를 여러 번 실어 보내는 것이 계약의 전부이고, 받은 쪽이 그것을 어떻게 쓰는지는 에이전트의 몫입니다.

Overlay 는 좁히는 것이지 부재를 바꾸는 것이 아닙니다. 세 영역을 골랐다고 해서 “이 셋에 없으면 없다”가 되지 않습니다. 부재를 단정할 수 있는 것은 여전히 hop 0 전체 목록뿐입니다.

KNOWLEDGE_AGENT_URL 을 비워 두면 시작 버튼도 체크박스도 아예 안 그려집니다 — 눌러도 아무 일 없는 버튼을 두지 않기 위해서입니다.

2

Agentic AI 와 상호작용하는 방식

이 온톨로지를 걷는 것은 두 동작이고 그 외엔 없습니다. 표를 가져오거나, 문서를 읽거나. 엔진마다 다른 것은 그 두 동작이 어떻게 도착하는가뿐이라, 붙이는 길이 셋이고 뒤에 광고는 하나입니다.

MCP

Claude Code · Codex 등. 도구 둘, stdio, 설치 없음. .mcp.json 이 저장소에 있어 클론 + 승인 한 번이면 붙습니다.

붙여넣기

MCP 없는 아무 에이전트. 지도의 Copy for an agent 가 같은 시작 블록을 GET URL 형태로 줍니다.

런처 URL

런을 받는 콘솔. 고른 영역이 ?root= 로 실려 갑니다. 위 Overlay 가 이 길입니다.

sequenceDiagram
  participant A as 에이전트
  participant K as Knowledge
  A->>K: knowledge_table()  — 인자 없음
  K-->>A: hop 0 — 영역 목록 + use_when
  Note over A: 조건이 맞는 한 줄을 고른다
  A->>K: knowledge_table("/v1/regions/library")
  K-->>A: 그 영역이 담은 것. 각 행이 자기 주소를 들고 있다
  Note over A: type 이 어느 도구를 부를지 말한다
  A->>K: knowledge_read("/v1/nodes/loan-desk/body")
  K-->>A: 문서 그 자체

행마다 붙는 type 이 불렀을 때 무엇이 나오는가를 말합니다. 위치가 아니라 결과에서 오는 값입니다.

type뜻에이전트가 할 일
dr자식이 있다knowledge_table — 들어간다
data본문이 있다knowledge_read — 읽는다
empty아직 아무도 안 썼다부르지 않는다. 그게 찾던 것이면 없다고 말한다

세 번째가 아끼는 것이 실제로 보입니다. Claude Code 에게 도서관 대출 규정을 물었을 때 스스로 이렇게 답했습니다 — /v1/nodes/shelving 은 아직 작성된 내용이 없어서 열지 않았습니다. 한 홉을 아꼈습니다.

어느 엔진이든 지켜야 할 규칙 둘

  1. 주소를 조립하지 않습니다. 모든 행이 자기를 가져올 주소를 인쇄합니다. 이걸 어기면 조용히 깨집니다 — 실제로 문서가 한 단계 아래로 옮겨졌을 때, 경로를 직접 만들던 소비자가 에러 없이 빈 답을 냈습니다.
  2. “없다”고 말할 수 있는 건 hop 0 뿐입니다. 개별 영역 표에서 못 찾았으면 돌아가는 것이지 없는 것이 아닙니다.

그리고 읽기 전용입니다. 쓰기는 git 에 커밋되고 작성자가 남는데, 에이전트가 자기를 조종하는 것에 무인으로 쓰는 건 선택해서 켜는 일이지 기본으로 얻을 일이 아닙니다.

MCP 에는 시스템 프롬프트가 없습니다. 그런데 이 구조는 에이전트가 결정하기 전에 영역 목록을 보는 것에 전부 걸려 있습니다. 그래서 영역 목록을 knowledge_table 의 설명문에 실어 보냅니다 — 모든 MCP 클라이언트가 모델에게 보여주는 유일한 텍스트라서요. tools/list 할 때마다 갱신됩니다.

모든 표와 출력은 실제 동작 결과입니다. 확인: check/mcp-check.py 가 프로토콜과 에이전트의 걷기를, check/smoke.sh 가 API·에이전트·화면을 봅니다.
