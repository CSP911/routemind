# Fixing one sentence in the routing table — before and after

    before  fingerprint a84ac6cf463a1a6d   mapcheck R6 FAILS (carried)
    after   fingerprint 2e0e821a7d9f667b   mapcheck R6 passes, 38 pass / 0 fail
    questions identical · hop 0 maintained · claude-sonnet-5 · one fresh session per question

**These are two corpora and the numbers do not merge.** The 700-question census belongs to the
first fingerprint and stays there. This is a before/after on one lever, ten questions, run to answer
one question: does correcting the note fix the miss?

## What was wrong

`hard-moved-overtime` and `hard-moved-threshold` are forwarding notes. They sit in the area a
subject moved *out of* and tell a walk where it went. Both said:

> They remain correct for anything dated before **2026-01-01** and for nothing after it.

That is false. The page left behind is the **oldest** of three versions and stopped being correct at
**2024-07-01** — eighteen months before the move the note describes. The note is not wrong about the
move. It is silent about a revision that happened before it, and silence reads as "nothing else to
know."

## What it cost

One walk in 700 — `t-overtime-08`, *"I have a claim dated in 2025 and I am not sure which version of
the overtime rate applies to it."* The agent opened payroll, read the note, did exactly what it said,
and answered from the 2023 rule.

**Both routing arms failed it, identically.** `routing` and `routing+overlay`, two agents sharing
nothing, one of them carrying a working set — same question, same two documents, same wrong era.

That symmetry is the finding. A working set cannot help, because nothing was forgotten: the note was
read, understood, and obeyed. The defect is not in the reader. **It is in the map.**

## Why this is the critical failure mode, and not a small one

Routing's whole claim is that a maintained table lets an agent go straight to the right document
instead of ranking a haystack. The census backs that claim hard — `indirect` 0.028 for fusion
against 1.000 for routing, on 320 questions each.

The same mechanism is the exposure. **An agent that trusts the map inherits the map's errors, and
inherits them silently.** Retrieval scored 1.000 on this lever precisely because it does not read
the note; it has no map to be wrong. Routing read a sentence, believed it — correctly, on the
evidence in front of it — and produced a confidently wrong answer with a citation attached.

So the two arms fail in opposite directions and the difference matters:

| | how it fails | what the user sees |
|---|---|---|
| retrieval | the right document is not in the top ten | an answer built from whatever was |
| routing | the map sends it somewhere plausible and wrong | an answer built from the wrong era, **with a source** |

A wrong routing table does not degrade gracefully. It does not return a worse ranking; it returns a
confident answer from the wrong place, and the walk report reads as a clean success. In this census
it was 1 in 700 — because the table was otherwise accurate. That number is a property of the table's
condition, not of the method, and it is exactly why `mapcheck` runs **before** the arms and why a
known failure now has to be carried by hand on the command line.

## The fix

The note now names every version it is silent about:

    | in force                 | where                                   |
    | until 2024-07-01         | the pages above, here in payroll        |
    | 2024-07-01 to 2025-12-31 | hard-overtime-v2, in attendance         |
    | from 2026-01-01          | sec-hard-overtime, in attendance        |

and says outright: *"a question dated anywhere after 2024-07-01 is answered in attendance, not here —
including dates before 2026-01-01, which is the case this note used to get wrong."*

`mapcheck` R6 enforces it from the corpus: a forwarding note must name every date its subject's own
revision legend names. Before the fix, both notes failed and the census ran with `--carry R6`. After,
38 pass and 0 fail with nothing carried.

## Result

Ten `changed` questions, re-walked on the fixed corpus:

| | before (`a84ac6cf`) | after (`2e0e821a`) |
|---|---|---|
| `changed`, routing | **0.900** (9/10) | **1.000** (10/10) |
| `mapcheck` R6 | fails, carried by hand | passes |

`t-overtime-08` is the one that moved, and the path shows why:

    before   hard-moved-overtime → payslip-overtime                              the 2023 rule
    after    hard-moved-overtime → hard-overtime-legend-revision → hard-overtime-v2   the 2025 rule

**The same note, and a different destination.** The agent did not become more careful; it was given
a sentence that was true. Its own account of the first step:

> `/v1/nodes/hard-moved-overtime/body` (payroll) — pointed away from payroll to attendance, flagged
> three versions exist

Before the fix, the note pointed away from payroll too — and said the page left behind was good
until 2026-01-01. Both walks obeyed. One was wrong because the sentence was.

## What ten questions do and do not settle

**Ten.** One lever, one run each, on a corpus that differs from the census by two documents. It
shows the fix works on the case that broke; it is not a re-measurement of anything else, and the
census's 0.999 belongs to the old fingerprint and stays there.

**The other six levers were not re-run.** The change touches two forwarding notes in `payroll` and
`approval`; `indirect`, `stale-old` and the rest never read them. Nothing here says those numbers
moved, and nothing here says they did not.

**A passing check is not a correct map.** R6 now passes, which means the notes name every date the
revision legends name. It does not mean every sentence in the table is true — only that this class
of silence is gone, and that a future corpus cannot reintroduce it without the gate refusing.
